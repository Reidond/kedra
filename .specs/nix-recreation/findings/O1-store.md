# O1 — store, derivations, references and collection

Research only, 2026-10-01. Kedra base: `main`, `b224d5711e857f7dbcaabf7ed42870916525800c`. Assigned sources: S-012, S-015–S-018, S-022. The supplied PDFs are authoritative; extracted text was read by PDF page, with direct PDF extraction spot-checks at S-012 PDF121 and S-017 PDF5. No implementation, build, benchmark, migration or runtime qualification was performed. The coordinator owns shared worklog/status updates.

**Recommendation:** implement a small independent realization/store core with an explicit intermediate build representation, initially input-addressed outputs plus separately verified content hashes. Package recipes, platform isolation, bootstrap material and Kedra system activation remain distinct work. Present Tvix is useful implementation evidence and a possible compatibility-library dependency; the inspected revision is not evidence of a usable replacement store/build engine.

### S-012 — The Purely Functional Software Deployment Model

[Verified supplied PDF](../sources/papers/phd-thesis.pdf); [canonical source](https://nixos.org/~eelco/pubs/phd-thesis.pdf). Eelco Dolstra, Utrecht University doctoral thesis, 2006. **Focused coverage, not exhaustive:** pointer discipline §3.4–3.5; store/atoms/derivation construction and relevant realization portions §5.1–5.5; GC §5.6; extensionality §5.7; selected content-addressing material §6.1, §6.3–6.4; platform, standard environment, bootstrap and impurity §7.1. Other thesis chapters and the complete security formalism were not independently analyzed.

- **Central; high:** recipe identity and realized content identity are different. Sources can be content-addressed while ordinary output paths are computed before execution from the derivation. Fixed-output derivations verify a promised digest and prevent a URL-only change from rebuilding downstream artifacts. Evidence: PDF105–106 / printed97–98 (§5.3), PDF108–114 / printed100–106 (§5.4). §5.7, PDF142 / printed134 explicitly treats behavioral equivalence of different outputs as a model assumption; an input hash is not a reproducibility proof.
- **Central; high:** canonical objects comprise regular bytes plus executability, directories ordered by bytewise names, and symlink targets; timestamps and most permissions are excluded. Evidence: PDF98–102 / printed90–94 (§5.2, Fig.5.2). Namespace and symbolic name enter the path identity; different store locations do not automatically exchange binaries. A store parent symlink can change embedded paths.
- **Central; high:** valid objects must exist, match recorded content hashes, and reference only valid objects; reference and referrer indexes must agree. Evidence: PDF103–105 / printed95–97, Invariants1–4. Registration is a transaction after successful completion, canonicalization and validation; checking validity again after acquiring the output lock prevents concurrent writers from replacing a winner. Evidence: PDF106–108 and PDF119–121 / printed98–100,111–113. The power-loss claim on PDF121 is conditional on filesystem durability; database atomicity alone is insufficient.
- **Central; high:** output references are scanned from the entire input closure, not merely direct declared inputs. Build-only tools need not enter the runtime closure. The serialized object scan also covers names and symlink targets. Evidence: PDF113–114 and PDF121–122 / printed105–106,113–114. ASCII scanning misses hidden, encoded or compressed paths, and outside-store dependencies; its effectiveness is empirical for supported packages, not universal. Evidence: PDF65–67 / printed57–59; PDF187–188 / printed179–180.
- **Central; high:** creating a root after returning an unprotected result races GC. Temporary roots protect objects before use/construction; permanent-root creation and temporary-root discovery require synchronization. GC invalidates/deletes referrers before their dependencies, preserving closure even if interrupted. Evidence: PDF133–142 / printed125–134 (§5.6, particularly Fig.5.21 PDF138). Self-references are allowed; the historical proof excludes nontrivial cycles. Open-program rooting is a platform issue, not a consequence of a profile symlink (PDF134–135).
- **Central; high:** content-addressed derived outputs require more than renaming an output to its digest. Self-references require special hashing/rewriting, and a derivation can map to multiple content realizations. Evidence: PDF143 / printed135 labels the intensional system a rough prototype; PDF151–154 / printed143–146 gives hash-modulo-self and equivalence-class handling. These are historical mechanisms, not a statement of today's experimental feature status.
- **Central; high:** bootstrap binaries are retained inputs at a declared trust boundary; a manager cannot manufacture its first compiler/libc from nothing. The Linux example injects static tools as atoms and then builds the standard environment. Platform libraries, ELF loaders, RPATHs and external dependencies remain packaging work. Evidence: PDF177–179 / printed169–171; PDF185–188 / printed177–180. This historical platform discussion does not establish current Darwin/Windows support.

### S-015 — Efficient Upgrading in a Purely Functional Component Deployment Model

[Verified supplied PDF](../sources/papers/eupfcdm-cbse2005-final.pdf); [canonical source](https://nixos.org/~eelco/pubs/eupfcdm-cbse2005-final.pdf). Eelco Dolstra, CBSE2005. Coverage: motivation, design, patch chaining, base selection and experimental discussion, PDF1–15 (§§1–6 and conclusion opening).

- **Central; high:** changing a fundamental input causes downstream identities and builds to change. Binary deltas reduce distribution cost while retaining old objects; they do not eliminate rebuilds or authorize overwriting old paths. Evidence: PDF5–8 (§2–3).
- **Supporting; high:** patch canonical archives, choose download/patch chains by a weighted graph, fall back to full transfer when bases are unavailable or mismatched. Base matching is heuristic; NAR canonicalization matters across directory renames and archive implementations. Evidence: PDF8–12 (§3–4), PDF15 (§6).
- **Supporting; high:** the experiment covers 50 historical releases and selected upgrade comparisons. Patch creation costs CPU/memory; major compiler changes reduce effectiveness, and duplicate storage remains a separate issue. Evidence: PDF13–14 (§5, Table1). **Inference; medium:** defer deltas and deduplication until correct full-object transfer and workload measurements exist; do not use these 2005 results as a Kedra performance forecast.

### S-016 — Nix: A Safe and Policy-Free System for Software Deployment

[Verified supplied PDF](../sources/papers/nspfssd-lisa2004-final.pdf); [canonical source](https://nixos.org/~eelco/pubs/nspfssd-lisa2004-final.pdf). Eelco Dolstra, Merijn de Jonge, Eelco Visser; LISA2004. Coverage: store/user-space separation, expressions, implementation, substitutes and environment policy (PDF3–9 / printed81–87), conclusion limitations (PDF13 / printed91).

- **Central; high:** a simpler store-expression intermediate representation lets frontends evolve separately from realization and policy. The paper explicitly motivates alternative frontends. Evidence: PDF6–7 / printed84–85, “Building Components.” Its historical closure/store-expression format is not a present compatibility specification.
- **Central; high:** installation space contains immutable variants; a user environment selects a view. Cache substitution changes the way an output is realized, not the requested identity; build-only dependencies need not be fetched for a substituted runtime closure. Evidence: PDF3–5,7–9 / printed81–83,85–87.
- **Central; high:** profile rename changes one selection pointer atomically; retained generations permit rollback and retain GC roots. Evidence: PDF9 / printed87. **Inference; high:** this is not transactional restart of processes or rollback of mutable application data. The conclusion's secure-sharing prospect is future work (PDF13), not evidence that input addressing authenticates downloaded bytes.

### S-017 — Imposing a Memory Management Discipline on Software Deployment

[Verified supplied PDF](../sources/papers/immdsd-icse2004-final.pdf); [canonical source](https://nixos.org/~eelco/pubs/immdsd-icse2004-final.pdf). Eelco Dolstra, Eelco Visser, Merijn de Jonge; ICSE2004. Coverage: §§3–8, PDF3–9.

- **Central; high:** distinguish dependencies consumed at build time, retained into the runtime object, and supplied by runtime composition. A closure is reachability under actual retained references. Evidence: PDF3–4 (§§3–4).
- **Central; high:** long distinctive names make conservative scanning useful, but pointer hiding (including UTF-16/compression) can produce false negatives; arbitrary runtime lookup and non-store paths require another contract. Evidence: PDF4–5 (§5), PDF9 (§8). The authors' 135-component experience and 47-package comparison are limited historical evidence, not a completeness theorem.
- **Supporting; high:** relocating already-built artifacts requires rewriting embedded pointers and can break internal checksums; a consistent global namespace avoids that problem. Evidence: PDF5–7 (§§6–7). **Inference; high:** Rust-level portability does not imply binary ABI or namespace portability.

### S-018 — Integrating Software Construction and Software Deployment

[Verified supplied PDF](../sources/papers/iscsd-scm11-final.pdf); [canonical source](https://nixos.org/~eelco/pubs/iscsd-scm11-final.pdf). Eelco Dolstra; SCM-11,2003. Coverage: build/deployment boundary, graph construction, activation, binary sharing, barriers and prototype limitations, PDF5–6,10–12,15–16 (§§2–5,7).

- **Central; high:** this paper concerns **Maak, a Haskell prototype**, not a current Nix implementation. It motivates explicit cross-package graph dependencies and transparent reuse of prebuilt derivates. Evidence: PDF5–6,11–12 (§§2–5).
- **Supporting; high:** its update barriers intentionally suppress propagation of selected changes; derivates can be overwritten and reconstructed from recorded attributes. Evidence: PDF11–12. **Inference; high:** these predecessor mechanisms conflict with the proposed strict immutable identity contract and should not be imported silently. Sharing security and scalability are acknowledged future work, PDF15–16.

## Proposed Rust boundaries — design inference, not implementation

Keep one flat-source reusable crate initially, with internal modules; do not begin by distributing six services or a permanent daemon. Stable wire formats and adapters can be added after a second consumer demonstrates a real boundary.

| Boundary | Minimal responsibility | Refusal / invariant |
|---|---|---|
| Identity and plan | Validated `BuildSpec`, `DerivationId`, named `OutputId`, `TreeDigest`, platform/namespace types; versioned canonical encoding | Distinguish ordered argv from sets/maps; reject unknown schema, ambiguous names, unsupported platform and graph cycles. Do not hash incidental configuration syntax. |
| Object admission | Snapshot inputs; canonical tree hash, bounded safe import/export, explicit references, immutable receipt | Reject unsupported node/metadata forms, traversal, missing references and hash mismatch; never follow an imported symlink while extracting. Runtime references and their authenticated receipt cannot be replaced by a bare content digest. |
| Realization | Resolve static input DAG; cache/build choice; bounded workers and cancellation; collect build result | Failure never yields a valid result. An existing realization with different bytes is a divergence, not an overwrite opportunity. Preserve evidence and refuse ambiguous reuse. |
| Store and roots | One management writer, per-output coordination, durable registration/recovery, atomic generation selection, leases | Readers only consume committed objects. Acquire protection before checking/using a path; publish a permanent root before releasing temporary protection. |
| Collection | Explicit collection from profiles, rollback/image roots and in-flight leases | Revalidate liveness under synchronization; invalidate before removing bytes, referrers before dependencies. Reject unsupported cross-object cycles initially; self-references need explicit handling. |
| Platform executor | Native Linux sandbox/process adapter supplied to core | Restrict network, host files and credentials; an unavailable sandbox is an error, not a same-identity unrestricted fallback. The sandbox policy and bootstrap/runtime assumptions belong in identity. |

Two details require strengthening the draft proposal. First, **private staging must preserve the final logical output pathname**: for input addressing, mount private backing storage at that pathname inside the build namespace, then publish its physical backing. Passing a random staging pathname as the build prefix and renaming afterward leaves embedded paths broken (S-012 PDF151–152). Second, define metadata policy before treating a generic object as an OS tree: the historical NAR model excludes ownership, SELinux labels, capabilities and special nodes. Kedra's image composition must explicitly restore/derive required OS metadata under its existing trust boundary, or a different canonical artifact schema must bind it. An executable bit alone is not a whole-OS serialization contract.

A pinned Fedora builder root is a reasonable **coarse declared bootstrap dependency**, not a claim that its RPMs already form independent immutable package closures. Native Linux on the two Kedra architectures is the first plausible support boundary. Kernel/driver facilities, device availability and runtime ABI requirements must be declared/qualified separately from target strings. Arbitrary native Darwin/Windows compatibility and cross compilation require additional evidence.

Compatibility decisions are independent: Nix language syntax, nixpkgs semantics, derivation/path encoding, NAR/cache transfer and familiar user workflows. Reusing `nix-compat` buys code for a specific Nix namespace/format commitment, with declared licensing and API-stability constraints. Reimplementing a small independent schema avoids that commitment but forfeits automatic nixpkgs/cache compatibility. Reusing `tvix-eval` only buys an evaluator candidate; allowed IO, builtins, package semantics, realization and OS composition remain work. A claim of complete compatibility needs end-to-end differential workflows, not API existence.

## Verification and handoff

Proposed future **E2E/manual** gates: two builds of a pinned real package and divergence handling; relocation-free execution from a imported closure on a clean compatible host; kill/disk-full at publication boundaries; two producers of the same output; collector racing build/import/profile switch and an executing old generation; import with invalid references and unsupported metadata; restart after interrupted deletion; native loader/library/bootstrap qualification. No such case was run here, and no unit/source-scanner acceptance is proposed.

O3 should reconcile historical addressing and GC mechanisms with S-019 current manual, especially floating content addressing, runtime roots, reference trust and metadata limits. O2 should retain separation between profile/store atomicity and OS activation/mutable-state rollback. The coordinator should archive the precise pinned URLs in the JSON companion and correct any proposal that describes current Tvix store/build components as available solely from the README. No new unassigned paper was adopted.
