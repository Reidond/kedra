# O2 — Declarative OS, modules, activation and services

Research only, 2026-10-01. Owner O2 analyzed S-004, S-005, S-007, S-010, S-014 and S-020 under the static manifest. Kedra is the target at inspected `main` base `b224d5711e857f7dbcaabf7ed42870916525800c`; Kedranix is reference only. Nothing below authorizes implementation, a new configuration language, OS migration, publication or installation.

## Result

A sharable Rust core can provide immutable build artifacts and a typed system-plan boundary while Kedra continues to compose, sign and deploy Fedora bootc images. That is a plausible first deliverable, not an independent NixOS-equivalent distribution. The important separation is **configuration evaluation → immutable construction → privileged activation → observed health**. Persistent application state and writable home sit outside the immutable construction model.

The full NixOS model includes a language, a module library, a package collection, platform-specific boot composition and stateful activation. Implementing a store/evaluator does not reproduce those surrounding systems. The recommendation is to preserve existing Kedra ownership and release contracts first and make any replacement frontend or whole-distribution backend an explicit later decision.

### S-004 — NixOS: A Purely Functional Linux Distribution, JFP 2010

Provenance: [verified: archived supplied full document](../sources/papers/nixos-jfp-final.pdf); [canonical URL](https://nixos.org/~eelco/pubs/nixos-jfp-final.pdf). Eelco Dolstra, Andres Löh, Nicolas Pierron. Journal of Functional Programming 20(5–6), 2010; DOI `10.1017/S0956796810000195`, verified in the archived official research index. The supplied manuscript header is dated 2 September 2010 and says it is under consideration; retain that distinction from final journal typesetting.

- **Central; high confidence — purity concerns static artifacts.** Sections 4.1–4.2, PDF12–16, and §5.2, PDF20–25, treat packages, generated configuration, jobs, kernel and initrd as nodes in one dependency graph. A generated SSH configuration references the exact xauth package and keeps it reachable. “Entire system” means the constructed static closure, not all live bytes or process state. Recommended inference: a `SystemPlan` must bind generated configuration to exact executable/library artifacts rather than merely recording a package name alongside unrelated text files.
- **Central; high confidence — modules are an extensibility mechanism above the store.** Section 5.1, PDF17–20: each module consumes the final `config` and package set, declares options, and contributes definitions. The option's merge function combines contributions; list concatenation is one example and module order affects list order. The merged result is fed back to modules. Section 6.3, PDF31–32, explains why lazy evaluation allows this configuration fixed point while actual option cycles remain errors. `mkIf` delays conditions at individual definitions to avoid premature recursion. Recommended inference: a sequential “apply modules to mutable config” loop is not a faithful NixOS module implementation. Do not silently promise Nix-compatible modules when implementing a much smaller Rust contribution API.
- **Central; high confidence — activation is outside the pure build.** Sections 4.2 and 5.2, PDF14–15 and PDF22–25: activation creates accounts, state directories and `/etc` links and changes services. The paper explicitly qualifies atomicity: the profile pointer can change atomically while a live switch can temporarily mix old and new services. Boot-time selection and live activation therefore have different guarantees. Recommended inference: retain separate build, stage, reboot/activate and health results, and record partial activation rather than claiming whole-system transactional rollback.
- **Central; high confidence — generations do not rewind databases.** Section 6.2, PDF28–29, excludes mutable `/var` from the functional model; §8, PDF35, identifies schema changes and reverse migrations as unresolved difficult work. Section 4.2, PDF15, retains old configurations only while their roots/closures survive. Recommended inference: home, keys, credentials, databases and other persistent data need distinct policies; deleting a generation also changes recovery availability.
- **Supporting; high confidence — Linux composition requires more than a package list.** Section 5.2, PDF23–24: kernel/module dependencies, a combined module tree, hardware-specific initrd contents, stage-one root mounting, stage-two activation and init/service management are explicit outputs. Section 6.2, PDF28–30: hard-coded paths and binary ELF interpreter/RPATHs require integration work; software outside the store can introduce undeclared dependencies. Recommended inference: prefix choice and host-versus-target environment are ABI/build-contract decisions, and successful construction does not prove bootability.
- **Supporting; high confidence — privileges are an activation concern.** Section 6.5, PDF33–34, excludes setuid binaries from immutable build outputs and places privileged wrappers in an activation-managed location, avoiding indefinitely callable vulnerable copies. Recommended inference: retain Kedra's narrow installed helper and image-owned trust; never execute an arbitrary plan's root shell fragments as a convenience.
- **Supporting; high confidence — type checking is not solved by the historical language.** Section 6.4, PDF32–33, describes a dynamically typed language, reflective module implementation and proposed stronger typing. A Rust implementation language does not make user configurations statically typed. Distinguish Rust API validity, option validation, graph validity and native configuration validation.

### S-005 — Hospital cloud deployment, ICSE CLOUD 2009

Provenance: [verified: archived supplied full document](../sources/papers/icse-cloud09-final.pdf); [canonical URL](https://nixos.org/~eelco/pubs/icse-cloud09-final.pdf). Sander van der Burg, Eelco Dolstra, Merijn de Jonge, Eelco Visser; 2009 ICSE Workshop on Software Engineering Challenges of Cloud Computing. DOI `10.1109/CLOUD.2009.5071534`, verified in the archived official index.

- **Supporting; high confidence — build composition and runtime placement are separate models.** Section 3.2, PDF4–5, distinguishes services/dependencies, available infrastructure and the mapping between them. It builds and transfers a service's closure before starting it. Recommended inference: an artifact identity should not contain accidental details of the currently selected deployment host unless those details are actual build inputs. Keep platform identity and target policy explicit, but do not add a fleet controller to Kedra.
- **Supporting; high confidence — atomic live upgrades require more than immutable paths.** Section 3.2, PDF5, describes a two-phase protocol with blocked incoming access while replacing services. This is the paper's protocol account, not an independently verified claim of arbitrary-service transactionality. O3 owns the referenced HotSWUp paper and its detailed limitations. Recommended inference: neither OCI replacement nor a store-profile switch alone proves uninterrupted or globally atomic services.
- **Tangential; high confidence — this is a prototype and research agenda.** Introduction, PDF2, and §4, PDF5, explicitly leave realistic evaluation, QoS-aware placement, dynamic discovery and persistent storage work open; the current generator described there is round-robin. Do not cite this as a production hospital deployment result or import its proposed distributed scope into the product.

### S-007 — NixOS: A Purely Functional Linux Distribution, ICFP 2008

Provenance: [verified: archived supplied full document](../sources/papers/nixos-icfp2008-final.pdf); [canonical URL](https://nixos.org/~eelco/pubs/nixos-icfp2008-final.pdf). Eelco Dolstra and Andres Löh; ICFP 2008. DOI `10.1145/1411204.1411255`, verified in the archived official index. This is the distinct two-author, 12-page conference paper, not the 38-page JFP manuscript.

- **Central; high confidence — preserve the historical model difference.** Sections 4–5, PDF5–10, give language syntax/representative operational semantics and an explicit system composition. The NTP example returns service properties, user requirements and an Upstart job; the top-level configuration distributes choices to subexpressions. The paper does not present JFP §5.1's later option-declaration/definition module framework. Recommended inference: cite S-004 for that module architecture rather than retrospectively attributing it to S-007.
- **Supporting; high confidence — stateful escape points are explicit.** Section 5, PDF8–10, constructs kernel/modules/initrd and configuration, then activates through accounts, symlinks and service changes. Section 6.2, PDF11, excludes mutable state and identifies fixed-path compatibility issues, ELF patching and a hardware-selected OpenGL escape point. Recommended inference: keep an explicit inventory of host/runtime dependencies rather than using “pure” as an absolute label for desktop behavior.
- **Supporting; high confidence — dependency determinism is not measured bit identity.** Section 6.2, PDF11–12, reports differences in repeated package builds, including timestamps and hostnames. The historical study's observations do not establish present reproducibility or Rust performance. Recommended inference: eventual reproducibility claims require actual repeated-build evidence from the new implementation. Testing detail was handed to the coordinator/O4 rather than duplicating their evaluation packet.

### S-010 — Purely Functional System Configuration Management, HotOS XI 2007

Provenance: [verified: archived supplied full document](../sources/papers/hotos-final.pdf); [canonical URL](https://nixos.org/~eelco/pubs/hotos-final.pdf). Eelco Dolstra and Armijn Hemel; HotOS XI, 2007. The official index links an ACM bibliographic record containing `10.5555/1361397.1361410`; no independently verified DOI registration is asserted here.

- **Central; high confidence — the useful unit is a closure of code plus configuration.** Sections 2–3, PDF2–5, extend immutable package construction to SSH configuration, service control and the bootable system. Changing a high-level option propagates through exact dependencies; old configurations coexist and can be selected. Recommended inference: reuse the build graph for native configuration outputs and their validators, not merely executable packages.
- **Central; high confidence — mutable mixed-purpose files break simple purity claims.** Section 4, PDF5, explicitly places `/var` outside the model and identifies the account database as mixed declarative/runtime state. Its activation depends on previous account contents. Recommended inference: model persistent identity and ownership allocation as effects, not as a hashable replacement of the live account database.
- **Supporting; high confidence — operational and spatial costs remain.** Section 3, PDF4, describes build, activation, test and retained boot entries; §4, PDF5–6, notes that changes deep in the dependency graph can require a large rebuilt closure. Recommended inference: plan disk-pressure and retained-recovery behavior before calling generational updates cheap; these historical sizes are not Kedra capacity estimates.

### S-014 — Service Configuration Management, SCM-12 2005

Provenance: [verified: archived supplied full document](../sources/papers/servicecm-scm12-final.pdf); [canonical URL](https://nixos.org/~eelco/pubs/servicecm-scm12-final.pdf). Eelco Dolstra, Martin Bravenboer, Eelco Visser; 12th International Workshop on Software Configuration Management, 2005. No DOI verified in this packet. Venue location is omitted because the archived index and a later paper's bibliography disagree.

- **Central; high confidence — service descriptions bind artifacts to external state.** Sections 2.1–2.4, PDF3–8, separate software/configuration/control components from persistent service data and describe build-new, stop-old, start-new. Immutable composition captures executable and configuration versions together; initialization/start/stop are separate control operations. Recommended inference: expose artifact construction and runtime effects through different APIs, with distinct error/recovery contracts.
- **Supporting; high confidence — compositional interfaces and shared parameters reduce drift.** Sections 3–4, PDF9–11, compose configuration fragments under an explicit subservice contract and derive repeated values such as a port from one parameter. Recommended inference: validate typed native service settings before rendering; do not invent an unrestricted configuration language just to share a value across renderers.
- **Central; high confidence — reload is an explicitly safe optimization, not an identity consequence.** Section 6.2, PDF14–15, sketches indirection for reloadable configuration and a conservative dependency-difference rule: restart when code/dependencies change. This is a proposed technique in the discussion, not a proved universal reload algorithm. Recommended inference: default to a known safe backend action and allow reload only when a service adapter declares and qualifies it; state compatibility still needs separate handling.

### S-020 — Observed modern NixOS manual

Provenance: [verified: official manual](https://nixos.org/manual/nixos/stable/), observed 2026-10-01: **Version 26.05**, generator `nixos-render-docs 26.05.3869.95ca1e203c07`; [retained HTML](../sources/web/nixos-stable-manual.html), SHA-256 `aacdf5ec7d2f7b425ec736aa74bbdfa53c81b8fee62d4fd5e3bf560212788aea`. Stable is mutable; this is not a newest-version claim. Confidence high for the observed document, not independently executed behavior.

- Types govern checking and merging; booleans require agreement after priorities. [Types](https://nixos.org/manual/nixos/stable/#sec-option-types).
- Lower override numbers win: ordinary 100, option default 1500, `mkDefault` 1000, `mkForce` 50. Ordering is separate: default 1000, before 500, after 1500. [Priorities](https://nixos.org/manual/nixos/stable/#sec-option-definitions-setting-priorities), [ordering](https://nixos.org/manual/nixos/stable/#sec-option-definitions-ordering).
- `mkIf` delays individual definitions. [Conditionals](https://nixos.org/manual/nixos/stable/#sec-option-definitions-delaying-conditionals).
- Live switching sequences systemd actions and activation; user services only receive daemon reload. [Switch](https://nixos.org/manual/nixos/stable/#sec-switching-systems), [configuration changes](https://nixos.org/manual/nixos/stable/#sec-changing-config).
- Persistent state extends beyond the store; boot artifacts and identity state matter. [State](https://nixos.org/manual/nixos/stable/#ch-system-state).
- Bootspec offers a versioned boundary, not automatic bootloader/Secure Boot composition. [Bootspec](https://nixos.org/manual/nixos/stable/#sec-bootspec).

Recommended inference: compatibility requires a pinned semantic target, not a generic “merge dictionaries” implementation. Existing Kedra deployment and state boundaries remain the default.

## Proposed typed boundary — inference, not approved implementation

Use separate value types, with private constructors enforcing their invariants. The following is an API sketch in prose notation, not executable code or a proposed user language:

```text
ResolvedModuleInput = pinned source + target facts + resolved typed option values
ModuleContribution = artifact requests + native service/settings contributions
                     + assertions + source locations
SystemPlan = schema version + target architecture + store ABI/prefix
             + exact external-input identities + build graph root
             + filesystem ownership plan + service graph + boot intent
             + persistent-state declarations + home baseline reference
             + policy/capability requirements + diagnostics/provenance
BuiltSystem = validated SystemPlan identity + realized closure/material evidence
DeploymentIntent = BuiltSystem + target backend + requested transition
DeploymentReceipt = observed staged/booted/healthy identity + effect outcomes
```

`ArtifactRef`, `StoreObjectId`, `TargetArchitecture`, `UnitName`, `ImageOwnedPath`, `PersistentPath`, `SecretRef`, `HomeBaselineRef` and `ExternalInputDigest` should be distinct concepts. A `SecretRef` must not expose content through generic artifact rendering. The filesystem plan needs conflict detection, ownership/mode and security-label expectations, and a clear refusal for overlapping image-owned and persistent paths. Native settings can be represented by typed adapters and existing native formats; an arbitrary JSON value is not enough to guarantee service validity.

The build core receives resolved inputs and constructs artifacts. A backend validates whether it supports the plan before any privileged change. Preserve argument vectors, explicit dependencies, bounded actions and source-linked diagnostics. Do not embed unrestricted root script execution in the common API. Systemd remains the service manager; the new core need not become a resident service manager or fleet daemon.

For the first Kedra frontend, lower the current explicit source plan, target metadata and native configuration into this boundary. A serialized plan is an internal versioned interchange format; it should not acquire imports, expression evaluation, arbitrary functions or implicit override rules. Calling a new user-authored option language “just a schema” does not avoid the existing prohibition on custom configuration languages.

| Frontend/model choice | What it buys | What it requires or does not provide |
| --- | --- | --- |
| Current Kedra source/native configuration → typed Rust plan | Smallest preservation of present contracts; sharable engine below product policy | No claim of Nix-language or full NixOS module compatibility; reuse remains at engine/plan level |
| Existing Nix frontend/library → the same typed boundary | Established expressions and module authoring model without inventing syntax | Explicit adoption decision; pin evaluator plus module/package library; retain lazy fixed-point/priority semantics in that frontend; inspect serialization and dependency context loss |
| New independent Rust module API | Compile-time types for known contributions, clear ownership and backend separation | Smaller semantics must be stated; arbitrary module fixed points, option type reflection and Nix compatibility do not follow from Rust |
| Custom user schema/DSL with imports, references, overrides and conditions | Potential tailored UX | Conflicts with the settled no-custom-language contract unless the owner changes it; substantial language/diagnostic/versioning work |

A bounded contribution API can offer explicit singleton conflict checks, ordered lists and keyed service maps. It must not silently use “last definition wins” for security settings. If a later owner decision requires true NixOS compatibility, preserve the frontend's final configuration fixed point and type-specific merging; do not replace it with a repeated convergence loop or claim a generic topological pass is equivalent. A strict independent model can instead reject cycles and require explicit dependencies, with that incompatibility documented.

## Fedora bootc staging and independent-OS hurdles

These are recommendations derived from the papers and inspected **local Kedra contracts**, not newly researched bootc implementation guarantees. Relevant local evidence: `usr/src/kedra/docs/ARCHITECTURE.md`, `image/Containerfile`, `image/assemble.sh`, and the current `kedra-bootc` skill. External bootc documents below are handoffs for later qualification.

1. **Start inside the build boundary.** Have the future Rust engine construct a small application/service closure and generated native configuration as reviewed image inputs. The existing Containerfile/Actions path remains the OS build, signature and publication authority. Keep the installed helper's exact-digest verification/staging. This permits testing the new build engine without replacing kernel, installer or security policy at the same time.
2. **Choose a store ABI before promising interoperability.** The logical runtime prefix is embedded in generated configuration and potentially ELF interpreter/RPATHs. An independent image-local prefix such as `/usr/lib/kedra/store` is only a candidate: it fits the current image-owned `/usr` boundary but requires build/runtime and SELinux validation. Nix-compatible `/nix/store` is a different contract; current Kedra source layout does not accept a root `nix/` payload. A writable `/var` store, an image store and a build-host physical store have different lifetime, trust and early-mount requirements. Do not claim relocation or Nix cache compatibility without O1/O3 evidence. Do not allow two independent garbage collectors to delete deployment-owned closure members.
3. **Keep writable state explicit.** Kedra's `/etc` merge semantics, persistent `/var`, journaled root state and ordinary writable home are current product requirements. A new immutable home baseline remains review material, not a symlink replacement of live home. Configuration rollback must not imply home/database/credential rollback. Persistent identity and schema compatibility require preconditions and separate recovery operations.
4. **Treat complete OS construction as a second backend.** It needs a package set and bootstrap toolchain, libc/loader contracts, kernel plus external-module compatibility, firmware, initramfs early storage/crypto/input/GPU support, root mounting, init/service units, login/PAM, desktop/native-app integration, installation media and update/recovery support. S-004 PDF23–24 and S-007 PDF8–9 justify this inventory; they do not provide a modern implementation of it.
5. **Preserve security properties deliberately.** Current Kedra requires enforcing SELinux and Secure Boot. New executable prefixes need security labels, policy transitions and a way to retain those labels through store import/image composition. Signed OCI trust and the firmware→shim→bootloader→kernel chain are separate. Current local architecture explicitly excludes initramfs, command line and root contents from that Secure Boot coverage; do not accidentally claim a stronger chain. Independent kernel/initramfs/bootloader composition therefore needs its own qualification and signing/retention design.
6. **Gate behavior with the established harness.** Use real CLI build/closure workflows, native service configuration checks, container sessions for installed behavior, and retained/disposable VMs for firmware, Secure Boot, SELinux, LUKS/login, boot/update/rollback and installer behavior. Include service restart failure, incompatible persistent state, power interruption, disk pressure, unknown plan version and stale-plan refusal. These are proposed later gates, all **not-run** here. No new custom test runner or source-text assertions are proposed.
