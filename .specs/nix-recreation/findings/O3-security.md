## S-001 — Secure Nix Expression Updates (2024)

[verified: https://landweber.xyz/ba.pdf] Local supplied document: `sources/papers/ba.pdf`, author/title/date checked at PDF1. Focused coverage: PDF16–32, chapters 3–6; diagrams and formal invariant included. Finn Landweber, bachelor's thesis, Leipzig University of Applied Sciences, 23 July 2024. No DOI verified.

**Author evidence.** The threat model permits a malicious central Git repository but excludes compromised developer machines/private keys and update availability/confidentiality (PDF16–17, §§3.2–3.3, printed14–15). It is narrower than arbitrary host compromise. The thesis distinguishes verifying one commit, authenticating ancestry with evolving committer permissions, and authenticating repository-reference operations; it does not equate a hash lock with developer authorization (PDF19–25, §§4.1–4.3). Git-Verify's out-of-band introduction bootstraps trust; accepting unsigned automatic merges creates a stated mix-and-match limitation (PDF21–24, §§4.2.1–4.2.5; PDF27, table5.1).

The most transferable finding concerns **verification placement**: an existing fixed-output result can satisfy another fetch without rerunning a signature check hidden inside that fetcher's builder. The proposed remedy downloads both payload and verification evidence, then verifies them in a separate ordinary derivation. The thesis's Git-Verify fetcher follows that separation; its Gittuf fetcher did not, and the author explicitly says not to rely on that implementation for verification (PDF29–30, §5.1.5, printed27–28). This is a dated implementation assessment, not a newly reproduced exploit or a claim about today's Gittuf.

Rollback protection requires the previous accepted state: the modified Niv checks that the previous commit is an ancestor before updating its lockfile. Branch/fork changes can require deliberate intervention. An authenticated old commit still passes signature verification, and indefinite freeze remains unresolved (PDF25–26, §4.4; PDF31–32, §§5.2–6). The conclusion's broad characterization of Nix security must remain dated to 2024.

**Current-doc bridge.** Nix 2.34.9 now explicitly documents experimental `verified-fetches`: `fetchGit.verifyCommit` checks the selected revision against supplied keys and rejects dirty local input; it defaults on when keys are supplied. This does not by itself document ancestry, release-channel freshness or revocation policy. [Built-ins, fetchGit](https://nix.dev/manual/nix/2.34/language/builtins#builtins-fetchGit).

**Proposed inference.** Keep immutable source identity, verifier identity/policy, accepted publisher keys, and monotonic update state distinct. Cache a verification receipt only when it binds all four relevant inputs, including verification evidence and policy version. Update authorization must execute even when source bytes are already cached. Keep explicit owner recovery/rollback separate from automatic update anti-rollback checks; ordinary rollback must not erase the high-water record. Freeze protection needs a declared freshness mechanism, not an assertion that a signature proves latestness.

## S-006 — Atomic Upgrading of Distributed Systems (2008)

[verified: https://nixos.org/~eelco/pubs/atomic-hotswup2008-final.pdf] Local supplied document: `sources/papers/atomic-hotswup2008-final.pdf`; focused coverage PDF2–5, §§2–7. Sander van der Burg, Eelco Dolstra, Merijn de Jonge; HotSWUp 2008. DOI verified from the archived official index: `10.1145/1490283.1490294`.

**Author evidence.** Immutable side-by-side packages plus replacing one profile symlink provide local namespace atomicity (PDF2–3, §2). Distributed deployment separates building/transferring complete closures from activation, then uses a two-phase-commit variant and exclusive profile locks (PDF4, §5). Crucially, installing files is insufficient: proxies must drain existing connections, block new ones, and expose the new services only after transition. The conclusion acknowledges that not every service activates simply by changing profiles; some require explicit stop/start or container restart (PDF5, §7).

**Limit.** PDF4 says failed commits roll cohorts back, but the paper does not specify durable coordinator decisions, partition reconciliation or uncertain-outcome recovery sufficient to establish this under arbitrary partial network failure. Its atomicity claim relies on the cooperating cohorts/proxies and controlled access described there. A lost response is not proof that the remote operation failed. Persistent application data is not shown to roll back transactionally.

**Proposed inference.** Reuse preparation-before-activation and explicit stage boundaries for a single Kedra host. Do not import a fleet coordinator, or call a profile rename an atomic service/data migration. Report prepared, selected, activated and healthy separately; an interrupted activation requires a journaled reconciliation path.

## S-013 — Secure Sharing Between Untrusted Users (2005)

[verified: https://nixos.org/~eelco/pubs/secsharing-ase2005-final.pdf] Local supplied document: `sources/papers/secsharing-ase2005-final.pdf`; focused coverage PDF4–10, §§2.3–8. Eelco Dolstra; 20th IEEE/ACM International Conference on Automated Software Engineering, 2005. No DOI verified.

**Author evidence.** The extensional model lets an input-derived pathname stand for a purported result. Sharing that result across users consequently shares trust in whoever supplied the binary (PDF4–5, §§2.3–2.7). The intensional model separates content identity from each user's accepted derivation-to-output mapping; different bytes occupy different paths. The mixed model adds explicit cross-user trust, rather than treating a content hash as evidence of source correspondence (PDF6–9, §§4–5). These are historical models; their per-user trust relation is **not** today's `trusted-users` administrator setting.

Local isolation includes preventing direct user store writes, distinct UIDs for concurrent builders, terminating residual processes before ownership/permission changes, and only then registering outputs. Permission changes do not revoke already-open writable descriptors; the order matters (PDF5–6, §3). Database validity excludes unfinished paths and preserves closure through transactions; the simplified algorithm omits implementation locks (PDF4, §2.5).

Content addressing with embedded paths requires self-reference normalization and hash rewriting, not simply hashing the finished directory. The paper's 86-component experiment reported functional results, but hidden/compressed references can defeat both rewriting and dependency scanning (PDF6–9, §§4.2–4.3,6.1). That historical experiment is not general compatibility proof. Hash collision resistance is an explicit assumption (PDF9–10, §6.2).

**Proposed inference.** The reusable core should distinguish recipe identity, actual object digest, dependency references and authenticated build provenance. It should never accept caller-owned bytes as a privileged build merely because a pathname matches. A content-addressed blob may be safely shared as bytes while its claimed relationship to a recipe remains untrusted.

## S-019 — observed Nix 2.34.9 reference manual

[verified: https://nix.dev/manual/nix/2.34/] Observed header **Nix 2.34.9**, accessed 2026-10-01. This is the selected version, not a claim that it is the newest release. Nix contributors; online reference manual. The following are current documentation statements, not executed interoperability results.

| Topic | Documentation evidence and bounded conclusion |
| --- | --- |
| Recipe versus output | A serialized derivation is content-addressed; its outputs need not be. Inputs are explicit, and the derivation creator must collect dependencies. A deriving path can identify an output before its store path is known. Higher-order deriving paths are experimental. [Derivations, Inputs/Encoding/higher-order](https://nix.dev/manual/nix/2.34/store/derivation/) |
| Input-addressed outputs | Addressing is based on the recipe, with quotient hashing substituting content identities for CA dependencies. Traditional paths are calculable before their build; dependence on floating CA inputs delays calculation until those inputs are realised. The manual flags a possible implementation/specification discrepancy for experimental multi-output CA. [Input addressing](https://nix.dev/manual/nix/2.34/store/derivation/outputs/input-address) |
| Fixed versus floating CA | Fixed-output builds check a predeclared digest and may fetch from the network; currently they have one `out` and no references. Floating CA outputs are experimental (`ca-derivations`); explicit impure floating builds require another experimental feature. A failed fixed hash does not establish the requested derivation result, even if fetched bytes are retained independently. [Outputs](https://nix.dev/manual/nix/2.34/store/derivation/outputs/), [Content addressing](https://nix.dev/manual/nix/2.34/store/derivation/outputs/content-address) |
| Content identity | A CA store path includes filesystem content, references, name and logical store directory; it is not a bare file digest. Self-references need special normalization. Reference support varies by hashing method. [CA store objects](https://nix.dev/manual/nix/2.34/store/store-object/content-address) |
| Content hashes versus provenance | `narHash` covers serialized filesystem data; references and optional content address are separate fields. The JSON format is experimental. `nix store verify` separately checks NAR content and trust; local builds, CA objects or accepted signatures can satisfy its trust test. This is not proof of reviewed sources or freshness. [Object metadata](https://nix.dev/manual/nix/2.34/protocols/json/store-object-info), [Verification](https://nix.dev/manual/nix/2.34/command-ref/new-cli/nix3-store-verify) |
| References and closure | Objects include their reference set; non-self cycles are forbidden, and present objects require their dependencies. **Inference:** a CA root can still reference an input-addressed object: do not infer cryptographic identity of every transitive byte from the root alone. [Store objects](https://nix.dev/manual/nix/2.34/store/store-object) |
| Builder processing | Inputs are realised first; outputs are locked, normalized and scanned for dependency hashes. Modes become read-only, setuid/setgid disappear. Scanning records candidate runtime references; it does not prove every semantically possible dependency was discovered. [Building](https://nix.dev/manual/nix/2.34/store/building), plus S-013 PDF9 for hidden references |
| Evaluator IO | Strings carry dependency context, including output and deep-derivation dependencies. Discarding context removes tracking. IFD can pause evaluation to realise a filesystem input; disabling it permits a complete plan before realisation. [String context](https://nix.dev/manual/nix/2.34/language/string-context), [IFD](https://nix.dev/manual/nix/2.34/language/import-from-derivation) |
| GC and generations | Roots retain their closures; retained generations permit rollback. `--add-root` creates indirect roots whose location must remain stable. Profile selection replaces one symlink atomically. These user-facing pages do not specify concurrent root-acquisition/deletion ordering. [Roots](https://nix.dev/manual/nix/2.34/package-management/garbage-collector-roots), [GC](https://nix.dev/manual/nix/2.34/package-management/garbage-collection), [gc command](https://nix.dev/manual/nix/2.34/command-ref/nix-store/gc), [Profiles](https://nix.dev/manual/nix/2.34/package-management/profiles) |
| Local-store boundaries | Direct local-store access exists without a daemon. Copying requires equal logical store directories; changing that path loses ordinary cache compatibility. Privileged runtime-root discovery is an issue for unprivileged GC; its external roots daemon is experimental. Unsafe writable temporary build directories are expressly warned against. [Local store](https://nix.dev/manual/nix/2.34/store/types/local-store) |
| Trust/isolation/durability settings | `trusted-users` is root-equivalent; build users are separate. CA objects bypass the ordinary signature requirement. Sandbox behavior varies by platform, configuration and fallback; fixed-output networking is exceptional. Metadata fsync defaults on, store-path fsync off. Pure/restricted evaluation are separate controls. [nix.conf](https://nix.dev/manual/nix/2.34/command-ref/conf-file#conf-trusted-users), [Multi-user mode](https://nix.dev/manual/nix/2.34/installation/multi-user) |
| OS metadata and secrets | The filesystem model has bytes/executable flag, directories and symlinks; NAR has no owner, general mode, xattr, label or capability fields. Secrets should stay outside the shared readable store and be supplied at runtime. [Filesystem model](https://nix.dev/manual/nix/2.34/store/file-system-object), [NAR grammar](https://nix.dev/manual/nix/2.34/protocols/nix-archive/), [Secrets](https://nix.dev/manual/nix/2.34/store/secrets) |

**Documentation caveats.** The outputs overview calls input addressing floating while also describing historical outputs as fixed; the dedicated input-addressing algorithm supplies the more precise dependency-sensitive account above. General introductory/building prose also simplifies outputs to input hashes. Do not use those summaries to erase fixed or floating CA distinctions. The reviewed pages do not completely specify cache-signature payload encoding, concurrent GC internals, or power-loss ordering. Exact compatibility would need pinned implementation/protocol inspection and executable fixtures in a later authorized phase.

## Proposed Kedra boundaries and future qualification

These are research inferences, not implemented capabilities:

1. **Reusable core:** typed immutable object/recipe identities, canonical serialization, reference graph, explicit accepted-result provenance and root/lease operations. Keep source-update policy and OS activation outside deterministic recipe evaluation. Network fetches accept expected content identities; update selection authenticates who authorized changing them.
2. **Privilege:** ordinary-user planning and isolated builders; an image-owned, short-lived helper owns privileged import/activation. No caller-controlled cache keys, helper executable, environment or mutable checkout may become root authority. Multi-user build coordination without a permanent daemon is possible as a design direction, but its locks, isolation and orphan cleanup still need qualification.
3. **Import and crash recovery:** stage privately; close every possible writer before validation; validate path types and traversal without check/use races; independently check content, references and accepted provenance; publish/register with documented flush and recovery ordering. Several renames plus a database transaction are not automatically one durable transaction. Unknown journal schemas and incomplete state must refuse safely.
4. **GC:** pin building/imported/staged/booted/recovery closures before making them externally usable. Coordinate root acquisition and deletion under one protocol. Preserve referrers until their deletion is committed before removing dependencies; refuse destructive GC if required root discovery is incomplete. A temporary process lease and a persistent rollback root have different lifetimes.
5. **OS composition:** a package NAR digest cannot authenticate Fedora SELinux labels, file capabilities, owners or arbitrary modes. Bind an explicit metadata/activation policy to the selected OS generation, or retain the existing authenticated image representation at that boundary. Keep runtime secrets out of source capture, serialized derivations, objects, logs and caches; carry secret references only.
6. **Required later evidence:** public CLI/container/VM workflows covering forged recipes/cache metadata, hash mismatch, cached-verification bypass, key/policy change, source rollback/freeze, residual builder writers, concurrent import/GC/root acquisition, interruption and ENOSPC at commit boundaries, unknown journals, missing closure entries, metadata restoration, and offline generation recovery. None passed in this research run. Service/data migration needs separate tests from store/profile selection.
