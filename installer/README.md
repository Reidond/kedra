# Local installer

Run `python3 installer/build-local.py --help`. [INSTALL.md](../docs/INSTALL.md) documents prerequisites, Secure Boot requirements and deliberate disk selection. On an Apple Silicon Mac, [utm/README.md](utm/README.md) runs this same entrypoint unchanged inside a disposable Linux container and prepares the UTM virtual machine.

The local entrypoint takes an explicit reviewed signed GHCR digest and a new output directory. The repository selects the target from the closed table in `build/release/material.py` (`desktop` x86_64, `utm` aarch64); other repositories are refused. The build host must match the target architecture, because the pinned image-builder only builds media for its own architecture. It checks the target's public key against `build/release/authority/<target>.sha256` and prints that fingerprint, enforces native signature/repository policy, requires the payload, builder and Anaconda environment to have the target's OCI architecture, extracts the signed payload's helper/source/trust without executing its programs, checks their target scope, and builds a separate Anaconda environment with the per-architecture builder digest from `inputs.json`. It writes one complete `kedra-<target>-44-<digest16>.iso` plus `installer.json` and `SHA256SUMS`, and never uploads.

`build-iso.sh` adds the required native SELinux-labeling stage. `anaconda-adapter.py` retains hash-guarded target scratch and persistent-mount preparation. `finalize-fstab.py` preserves physical /sysroot and read-only policy. Unsupported upstream changes fail. The Containerfile installs the signed cdboot GRUB for its own architecture (`gcdx64.efi` or `gcdaa64.efi`). It keeps `grub2-pc-modules` on both architectures: image-builder v82 always adds the i386-pc El Torito stage, and `org.osbuild.grub2.inst` reads `/usr/lib/grub/i386-pc` from this build root.

Fedora 44 aarch64 media and the test-signed fallback: shim-aa64 16.1-5 ships `fbaa64.efi` and `mmaa64.efi` signed only by a Red Hat test certificate, which shim does not trust. The installer ISO does not contain `fbaa64.efi`. The pinned arm64 builder's osbuild stage `org.osbuild.grub2.iso` fills `EFI/BOOT` only from `/boot/efi/EFI/fedora`:

- `shimaa64.efi` becomes `BOOTAA64.EFI`;
- `gcdaa64.efi` becomes `grubaa64.efi`;
- `mmaa64.efi` is copied unchanged.

It never copies the `EFI/BOOT/fbaa64.efi` that the Containerfile's `cp -ra` places in the build root. The source is `/usr/lib/osbuild/stages/org.osbuild.grub2.iso` in `ghcr.io/osbuild/image-builder@sha256:ed3364f3…`, read 2026-09-25, and it matches the aarch64 layout experiment, whose `EFI/BOOT` held only the binaries `BOOTAA64.EFI`, `grubaa64.efi` and `mmaa64.efi` besides the GRUB configuration and font. Shim 16.1 starts fallback only when `\EFI\BOOT\fbaa64.efi` exists next to it on removable media (`should_use_fallback`), so the ISO boots shim, then GRUB. Shim starts the test-signed `mmaa64.efi` only in two cases, and both stop with a Security Violation:

- a MokManager request is pending (for example after `mokutil --import` or `--disable-validation`);
- GRUB fails verification.

Kedra enrolls no MOK keys. The installed disk is different: bootupd puts `EFI/BOOT/fbaa64.efi` on its EFI partition, so it boots only through the NVRAM entry for `\EFI\fedora\shimaa64.efi`. Anaconda 44.30-2's bootc payload runs `bootc install to-filesystem` without `--generic-image`, and bootc then runs bootupd with `--update-firmware`, which writes that entry. This is read from the source and has not yet been observed on an installed `utm` system; see [utm/README.md](utm/README.md) for recovery.

The media uses Fedora's permissive installer SELinux environment; the installed system remains enforcing. Anaconda cannot start without UEFI Secure Boot and offline payload verification. `verify-payload.service` runs the helper's installer verification, which refuses unless the SecureBoot variable is 1 and SetupMode is 0 (`crates/sysroot-helper/firmware.rs`) and prints the reason and firmware guidance on the console. The drop-in `require-verification.conf` is installed for both Anaconda entry points, `anaconda.service` (the tmux session) and `anaconda-direct.service` (the `inst.notmux` path). Fedora 44's `anaconda-direct.service` has `Requires=anaconda.service` without `After=`, so it would otherwise start `/usr/sbin/anaconda` without waiting for verification. The drop-in requires and orders after that unit and independently asserts `AssertSecurity=uefi-secureboot`. The assertion sits on the Anaconda units rather than on the verification unit, because an unmet assertion stops a unit before its program runs and would hide the helper's message. A disabled, setup-mode or legacy BIOS boot therefore stops before installation. Check the gate in a built environment with `systemctl cat anaconda.service anaconda-direct.service`.

Optional `--smoke` boots the unchanged ISO as a CD through UEFI Secure Boot, with no direct kernel boot and no disks. On x86_64 it uses q35 with SMM, `OVMF_CODE_4M.secboot.fd` and a copy of `OVMF_VARS_4M.ms.fd`. On aarch64 it uses `virt` with `AAVMF_CODE.secboot.fd` and a copy of `AAVMF_VARS.ms.fd`. Both require KVM. QEMU passes the `kedra.research` system credential as SMBIOS type 11 (`io.systemd.credential:kedra.research=1`). That credential is `boot-probe.service`'s only trigger (`ConditionCredential=`), so the boot menu is unchanged. The probe writes to the virtio-serial port `org.kedra.events` (`/dev/virtio-ports/org.kedra.events`). It reports `KEDRA_INSTALLER_SECUREBOOT_ENABLED` only after reading SecureBoot 1 and SetupMode 0 from efivarfs and finding kernel lockdown in integrity or confidentiality mode. It then reports signed-payload verification and Anaconda startup. `installer.json` records the QEMU version and firmware file hashes. Manual testers can trigger the same probe with QEMU's `-smbios` option, or with `systemd.set_credential=kedra.research:1` on the kernel command line. Fresh encrypted installation and untouched-disk checks remain separate manual qualification.

Disposable experiment, 2026-09-25, TCG instead of KVM in an arm64 container with Ubuntu 24.04 QEMU 8.2.2 and firmware 2024.02-2ubuntu0.9. The smoke command lines were otherwise unchanged, and the Kedra ISO itself was not built or booted. Results:

- **x86_64:** the Fedora 44 GA netinst booted through shim and GRUB under Secure Boot. A credential-injected copy of this unit and probe (only the Kedra verify-unit checks removed) reported Secure Boot and then Anaconda startup.
- **aarch64:** a test ISO with the current base's shim-aa64 16.1-5, `gcdaa64.efi` 2.12-64 and signed kernel 7.2.7-200 booted with Secure Boot enabled. systemd 259.9 imported the credential, and the probe reported `KEDRA_INSTALLER_SECUREBOOT_ENABLED`. With the blank `AAVMF_VARS.fd` it reported `KEDRA_INSTALLER_PROBE_FAIL`.
- **Fedora 44 GA aarch64 netinst ISO (44-1.7):** its `/images/pxeboot/vmlinuz` has no Authenticode signature, so GRUB refuses it under Secure Boot (`bad shim signature`). Kedra media take the kernel from `/usr/lib/modules/<version>/vmlinuz` in the installer environment, and that kernel is signed. Do not use that GA ISO as a Secure Boot pre-check on aarch64.

Local end-to-end qualification must accompany changes to this entrypoint; syntax alone is insufficient.
