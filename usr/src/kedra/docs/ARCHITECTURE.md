# Architecture and safety contracts

Kedra is a personal Fedora 44 bootc OS. `sysroot` is its command; a narrow helper installed in the image performs the root operations of an update. Rust uses edition 2024, one Cargo workspace and lockfile, and explicit flat `main.rs`/`lib.rs` paths with no Cargo `src/` directories. There is no BlueBuild, custom Git engine, general configuration language, fleet service or permanent AI daemon. The one language exception, approved by the owner on 2026-10-06, is the versioned `.kedra` package language: Rust parses and type-checks it into engine data, author shell runs only inside an isolated engine builder, and the signer and helper never evaluate it.

## Source and ownership

The `.kedra` modules under `system/` declare every target: its packages, image files under `/etc` and `/usr`, home baseline and managed home files, units, image steps, published image, hardware status and foundation edits (os-release names, hidden autostart entries). Targets compose shared sets with `use`; a file declared twice is refused with both origins, never overridden. Small files are inline literals; larger and managed home files are `file("./…")` resources beside the modules. `crates/` (the Rust workspace) and `usr/src/kedra/` are the development tree and never enter the image; any other committed path, including root `etc/` and `usr/`, is refused. `sysroot source plan` records each image file's source file and declaring set, and generates the managed home list. Build contexts contain only declared payloads; the whole repository is never copied into an image.

`/usr` holds image-owned software, public trust and home baselines. `/etc` follows bootc's persistence and merge rules; `/var` and live home persist across deployments. Root state lives in `/var/lib/sysroot`; each user's applied home baselines are kept separately in that user's state directory. OS rollback does not rewind home, credentials, persistent databases or personal tools.

## Release authority

The independent `sysroot-engine` crate provides ordinary-user builds, an immutable store, runtime closures and profiles through `sysroot build`, `store`, `run`, `profile`, `develop` and `catalog` ([ENGINE](ENGINE.md)). Builds and commands run without a daemon in an unprivileged bubblewrap sandbox. Store objects carry content identity, never OS-signing or deployment authority, and engine profile rollback and garbage collection never touch bootc deployments, live home files or GHCR.

Both targets build through one engine pipeline in Actions, each natively on its own runner. A run resolves its Fedora RPM lock once, builds the foundation image offline from that lock, builds the `.kedra` catalog packages, composes them with the committed configuration, derives the image steps the target's catalog block declares (GLib schemas, systemd links, account skeleton, initramfs) and adds the public trust layer ([SYSTEM](SYSTEM.md), [NATIVE](NATIVE.md), [PACKAGES](PACKAGES.md)). The derivation runs only fixed image-local tools and records the bytes it generates; it does not widen the package sandbox. Generating the account skeleton never changes an existing home.

Each target's final OCI registry digest is signed with its own OS-image key: `desktop` (x86_64) and `qemu-arm64` (aarch64) each have a separate key, signing environment and GHCR repository. The `stable` tag only locates an image; the signature, the exact repository and digest, and the identity the image carries establish that it may be installed. The signed content binds the source revision and manifest (including home baselines), target, architecture, rank and resolved inputs. Image signing is separate from Secure Boot. Installer ISOs become GitHub Release assets only when the owner dispatches `iso.yml`; they carry no release signature, and the signed image they embed remains the authority ([RELEASES](RELEASES.md)).

Build jobs hold public trust only. After validation, the automatic signer runs no checkout, candidate binary or repository script while it holds the production key. Its environment deploys only from `main` and has no human-review gate. Serialized release runs and exact-source and rank checks prevent publishing a stale `stable`. Independent strict signature verification comes before `stable` moves. Unchanged inputs publish nothing; there is no checkpoint renewal. An uncertain registry write is reported as success only after an exact readback.

bootc verifies image signatures: the helper stages only an exact digest with `bootc switch --enforce-container-sigpolicy`, under the installed strict policy (one repository, the target's key, exact-repository identity). It refuses to run unless that policy matches the booted image's trust and no per-user container policy can override it. bootc does not order images, so the helper also refuses a candidate whose signed identity is out of scope or older than the booted image's. Root trust comes only from the booted image, never from a writable checkout, a user's home state or a caller's claim of verification. The only persistent root state is the rollback hold; unknown or corrupt state is refused. Rollback places updates on hold; staging and reboot stay explicit. See [UPDATES](UPDATES.md#how-an-update-is-verified).

Keep required image digests, signatures and local recovery media. There is no automatic garbage collection of signed images. Image signatures do not prove the upstream base is authentic; keep reviewed immutable base inputs. A source revision built against moving RPM repositories is not a bit-for-bit rebuild recipe; the image's RPM lock records what it installed.

## Installer

Anaconda media is built from an exact signed GHCR digest with a pinned builder into a new output directory: locally on demand, or by the owner-dispatched `iso.yml` from the target's current `stable` digest, which publishes it as GitHub Release assets. The media's own console and rescue privileges and its permissive SELinux setting do not change the installed system's enforcing SELinux or strict signature policy. The ISO verifies its embedded payload offline before installation and refuses to start unless it booted with UEFI Secure Boot enabled. There are no preset disk identifiers, no first-disk erase and no default owner password.

The pinned image-builder manifest receives a native SELinux-labeling stage where missing. Hash-guarded Anaconda adapters preserve the approved non-API mounts for account creation and supply target-backed scratch storage for the OCI import only after disk selection. Cleanup failures stop installation. The fstab normalizer addresses the physical root at `/sysroot`, preserves read-only policy and other mounts, and refuses unsupported input. See [bootc physical-root guidance](https://bootc.dev/bootc/bootc-install.html#finding-and-configuring-the-physical-root-filesystem).

## Writable home

Live files remain ordinary writable files. Never replace them with symlinks, whole-home capture or Git ignore/index flags. The image declares its managed home files as `managed` entries of `system/*.kedra`, generated into `/usr/share/kedra/home-files.toml`, each with optional check and reload commands; `sysroot` has no application-specific home code. Only declared files are read, so credentials, vault and keyring data, transcripts and caches stay out unless an entry names them. See [HOME](HOME.md).

`sysroot home update` merges installed baseline changes into live files with `git merge-file` against the last applied baseline, kept per user in `$XDG_STATE_HOME/kedra/home`. A candidate passes its declared check before an atomic replacement that keeps mode, group and SELinux label; reloads follow, and the new baseline is recorded only after all of them succeed. A conflict leaves the live file untouched and writes `<file>.kedra-new`; conflict markers never enter live configuration. `sysroot home capture` copies a live file into the checkout's source path for the owner to stage by line; it never commits. Accepting a baseline and publishing to source stay separate operations.

## Agents and credentials

Bundled agents are private executables reached through `sysroot`, not ordinary commands on PATH; personal runtimes and profiles remain independent ([AGENT-LAUNCHERS](AGENT-LAUNCHERS.md)). A profile directory is not a security sandbox. Repository development skills live in the `usr/src/kedra/plugins/kedra` and `usr/src/kedra/plugins/rust-skills` plugins, registered for this repository only; they are never copied into the OS, installer, home baseline or launcher profiles.

Bitwarden holds SSH keys. Never export private keys or pass an unlocked vault session to agents. SSH, GitHub API, registry, model authentication and OS-image signing are separate authorities. Account login is an owner operation; there is no custom OAuth or credential synchronization.

## Verification and recovery

Use real CLI, process and Git workflows and disposable VMs. Changes are tested locally and merge on their `signoff` commit status; Actions runs no test workflow for changes, only the container harness on each exact release candidate before signing. No unit, model, mock or doc tests, repository source scanners or custom test runner. Formatting, Clippy, builds and runtime validation remain required. A container build is not a boot test; a staged image is not running or healthy. Never enroll, format or apply home changes on the development workstation. Secure Boot is required, and every VM workflow boots with it enabled and the Microsoft UEFI CA keys enrolled. It covers firmware, shim, GRUB and the kernel plus kernel lockdown, not the initramfs, kernel command line or composefs root. Unknown hardware, key rotation and failure cases that have not run stay explicit in [STATUS](STATUS.md).
